# PriveTek

PriveTek проверяет данные пользователя в подключённых источниках, формирует PDF-отчёт и сохраняет его в личном кабинете. [Главная на Tilda](https://privetek.ru/) · [Личный кабинет](https://lk.privetek.ru/account)

## Как пользователь получает отчёт

1. Заполняет форму на главной без входа. При переходе в ЛК поля сохраняются на один час в том же браузере.
2. Создаёт аккаунт и подтверждает email кодом из письма либо входит в существующий аккаунт. При включённой двухфакторной аутентификации вход требует второго фактора.
3. Проверяет заполненные поля, даёт согласие и запускает проверку. Email берётся из подтверждённого аккаунта. Телефон необязателен. В ЛК можно указать до трёх разных username.
4. Открывает готовый отчёт в ЛК. Для новых отчётов раздел «Что проверено» показывает результаты, пропуски и сбои отдельных источников. Приложение также отправляет PDF через настроенный почтовый сервис.

Логотип в ЛК ведёт на главную. [Гостевая заявка и Tilda](GUEST_HANDOFF.md) · [Аккаунты и 2FA](ACCOUNTS.md) · [Форма заказа и статусы проверок](REPORT_FORM.md)

## Архитектура

Главная работает на Tilda, приложение и ЛК — на Render. Публичный адрес ЛК обслуживает прокси Timeweb.

- `server.py`: FastAPI, проверка формы и доступа, запуск фоновой обработки, API статуса для команды.
- `submission_guard.py`: подавление дублей и квоты одного процесса.
- `osint.py`, `source_checks.py`, `hibp_client.py`: проверки источников и явное указание недоступных проверок.
- `report_data.py`, `report_insights.py`, `pdf_gen.py`: подготовка данных и PDF.
- `email_sender.py`: HTTPS API Brevo либо SMTP с SSL/STARTTLS, проверкой сертификата и тайм-аутом.
- `account_routes.py`, `account_store.py`, `account_crypto.py`, `account_ui/`: регистрация, подтверждение email, пароль, сессии, личная история и защищённые PDF; настройки в ACCOUNTS.md.
- `job_store.py`, `migrations/`: PostgreSQL, текущий статус и история переходов без email, телефонов и содержимого отчёта.
- `privacy_logging.py`: журналы по идентификатору задания с удалением URL, email и текста исключений.

В рабочем сервисе включён ЛК (`ACCOUNTS_ENABLED=true`). Для локального запуска значения флагов и требования к БД описаны в [ACCOUNTS.md](ACCOUNTS.md). Ключ командного API и ключ вебхука задаются отдельно.

Обработка выполняется в потоках одного процесса, максимум четыре задания одновременно. Постоянная очередь и восстановление заданий после перезапуска не реализованы. Запись статуса в БД не является очередью: незавершённые задания после аварии требуют проверки командой.

## Установка и запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
cp .env.example .env
```

Заполните `.env` локально. На хостинге задавайте секреты в переменных окружения; они имеют приоритет над `.env`. Не публикуйте `.env`, строки подключения или ключи.

| Переменная | Назначение |
| --- | --- |
| `WEBHOOK_SECRET` | Обязательный секрет приёма заявок. Случайное значение минимум 32 символа. Без него POST возвращает 503, даже для test=test. |
| `DATABASE_URL` | Строка подключения PostgreSQL/Neon с TLS (`sslmode=require`; `verify-full`, если настроена проверка доверенного сертификата). |
| `REQUIRE_DATABASE` | `true` на Render: отсутствие БД запрещает запуск и приём заявок. `false` допустимо только для локальной демонстрации без сохранения статусов. |
| `STATUS_API_KEY` | Отдельный случайный ключ команды минимум 32 символа. Без него API статусов возвращает 503. |
| `MAIL_PROVIDER` | `brevo` для Render Free; альтернативно `smtp`. |
| `BREVO_API_KEY`, `MAIL_FROM` | Ключ Brevo и подтверждённый адрес отправителя. |
| `HIBP_API_KEY` | Необязательный ключ HIBP; без него HIBP пропускается с предупреждением; LeakCheck Public работает без ключа. |
| `HOST`, `PORT` | По умолчанию `127.0.0.1:8000`; Render задаёт порт, HOST в Blueprint равен `0.0.0.0`. |

Для SMTP нужны `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_SECURITY` (`starttls` или `ssl`) и при необходимости `SMTP_PORT` (обычно 587 или 465). OAuth для SMTP не реализован.

```sh
python server.py
```

GET `/` возвращает `ok`. Если БД настроена, проверяется доступ к таблице заданий; недоступная БД даёт 503. Проверка не подтверждает исправность поисковых источников и доставку почты.

## PostgreSQL и миграции

При запуске выполняются SQL-файлы `migrations/` в порядке имён. Версии сохраняются в `privetek_schema_migrations`; применённые миграции повторно не выполняются. Применение защищено транзакционной блокировкой. Новые изменения схемы добавляйте отдельными файлами, не переписывайте применённые миграции.

`001_jobs.sql` совместима с существующей таблицей `privetek_jobs`; `002_job_events.sql` добавляет историю `privetek_job_events`. История начинается с установки этой версии и не восстанавливает прошлые переходы.

Текущий статус и новая запись истории сохраняются в одной транзакции. Записываются только ID, статус и время. Соединение и SQL ограничены тайм-аутами; сохранение принятой заявки вынесено из цикла обработки HTTP в отдельный поток.

Статусы: `accepted`, `searching`, `generating_report`, `sending`, `provider_accepted`, `failed`, `delivery_unknown`. `provider_accepted` означает принятие письма провайдером, а не получение адресатом. `delivery_unknown` требует проверки журнала провайдера до повторной отправки.

## Подключение Tilda

Текущая главная загружает скрипт ЛК, который переводит её форму на HTTPS POST `/account/start`. Данные передаются в теле запроса. Готовая форма доступна и по прямому адресу [lk.privetek.ru/account/start](https://lk.privetek.ru/account/start). Инструкция по публикации и проверке — в [GUEST_HANDOFF.md](GUEST_HANDOFF.md).

При включённом ЛК старый `POST /webhook` с рабочей заявкой отвечает 409 и указывает на новый сценарий. Авторизованный проверочный запрос интеграции по-прежнему отвечает 200 без запуска поиска.

Сервисы Render Free могут засыпать между обращениями. Перед демонстрацией откройте ЛК и дождитесь загрузки.

## Аналитика привлечения

Размеченные ссылки `/go?utm_source=…&utm_medium=…&utm_campaign=…` фиксируют переход и ведут на главную. Внутренняя сводка показывает посещения и регистрации по каналам, принятые заказы, готовые отчёты, выдачу PDF и число заказов по аккаунтам. События отражают отдельные этапы. Выдача PDF означает ответ сервера с файлом.

Команда получает сводку через `GET /api/internal/analytics/summary?days=30` с ключом командного API. Примеры ссылок, определения метрик и CSV-экспорт описаны в [ANALYTICS.md](ANALYTICS.md).

## API статуса для команды

GET `/api/jobs/{job_id}` требует `Authorization: Bearer ВАШ_STATUS_API_KEY`. Передавайте ключ только по HTTPS в заголовке. Не используйте его в клиентском коде публичного сайта и не передавайте ключ вебхука вместо него.

Ответ содержит `id`, `status`, `created_at`, `updated_at`, `history` с записями `status` и `created_at`. Время БД возвращается с часовым поясом. Email, телефон и PDF через API не выдаются.

403 — неверный или отсутствующий ключ; 404 — неверный ID либо нет такого задания; 503 — нет ключа команды, БД или БД недоступна. Ключ команды обеспечивает общий служебный доступ; индивидуальный аудит сотрудников и роли не входят в первый этап.

## Квоты и безопасность

- Тело заявки максимум 16 КиБ, файловые вложения запрещены.
- Email валидируется; телефон нормализуется в международный формат. Это не подтверждение владения адресом или номером.
- 2 новые заявки на email в час, 20 на процесс в час, 4 одновременно. Превышение квоты — 429 с Retry-After; перегрузка — 503.
- Одинаковые email, телефон и username получают один ID во время работы и ещё 10 минут после завершения, включая ошибку. Повтор помечается X-Duplicate: true.
- Квоты и дубли хранятся в памяти, используют HMAC вместо исходных адресов и сбрасываются при перезапуске. Нужен один процесс.
- SQL использует параметры; ключи берутся из окружения. HTTPS завершается на хостинге/прокси, SMTP использует проверку сертификата.
- Временный PDF удаляется после фоновой обработки, включая ошибку почты. При включённом кабинете зашифрованная копия хранится 30 дней (ACCOUNTS.md). После аварийного завершения процесса временные файлы могут остаться; папку reports нельзя публиковать как статические файлы. Автоматического повторного письма нет.
- Перед запуском проверки в рабочем ЛК нужны аккаунт с подтверждённым email и явное согласие пользователя. Телефон и username отдельно не верифицируются.

Логи содержат ID заявки, результат отправки и безопасный тип ошибки с этапом. Срок хранения журналов, оповещения и доступ команды настраиваются на хостинге отдельно.

## Проверки

```sh
python -m pytest -q
python -m pip check
```

Тесты не отправляют письма и не ищут реальные персональные данные. Проверяются валидация, Tilda-совместимые формы и повторы, обязательная защита (включая probe), отдельный доступ к статусам, логирование, очистка PDF после успеха/ошибки, SQL-параметры и порядок миграций. Проверки БД в основном наборе используют имитацию соединения и не подтверждают работу PostgreSQL на хостинге.

Для сквозной проверки используйте тестовый аккаунт: начните заявку на главной, проверьте сохранение полей при входе или регистрации, запустите проверку с согласием и скачайте PDF в ЛК. Статус задания можно сверить через командный API. Доставку письма подтверждайте в почтовом ящике.

Без сети и почты:

```sh
python demo_report.py
python demo_grouped_report.py
```

## Источники и отчёт

В реестре 17 сервисов: HIBP, LeakCheck, Instagram, Amazon, Spotify, Gravatar, GitHub, GitLab, Codeberg, Hugging Face, DEV, Hacker News, Keybase, Lichess, Chess.com, Wikipedia и Discourse Meta. Возможности, передаваемые данные и ограничения описаны в [SOURCES.md](SOURCES.md); доступность внешних источников не гарантируется. Ошибки источника не считаются отрицательным результатом. Gravatar получает SHA-256 нормализованного email; это псевдонимизация, а не анонимизация. На сайте нужно пояснить передачу данных сторонним источникам.

Отчёт группируется по виду проверки, показывает находки, возможные совпадения и ограничения отдельно. Время проверки указано в UTC; дата утечки — отдельно. Точные дубли результатов удаляются без объединения личностей. Наличие аккаунта не доказывает личность владельца.

Документация: https://haveibeenpwned.com/API/v3 , https://docs.gravatar.com/sdk/images/ , https://render.com/docs/free , https://developers.brevo.com/reference/send-transac-email .

## Этап 1: MVP поиска

`osint.search(email=None, phone=None, username=None)` поддерживает отдельные идентификаторы и их комбинации. Email в Webhook обязателен как адрес доставки отчёта и также проверяется. Phone нормализуется в E.164 и проверяется через Amazon; Instagram по телефону отключён как ненадёжный. Username необязателен: 1–64 латинских букв/цифр/точек/дефисов/подчёркиваний, начинается с буквы или цифры. Начальный @ удаляется, регистр сохраняется для сайтов с чувствительными к регистру именами. Проверяются 11 публичных API; каждый адаптер отдельно проверяет формат своей площадки. Произвольные URL не принимаются. Email дополнительно проверяется через LeakCheck Public с передачей первых 24 символов SHA-256; значения данных утечек не запрашиваются.

Единый результат имеет `schema_version: 1` и `checks`: `source`, `source_url`, `kind`, `status`, `reason`, `checked_at` (UTC или null для непроведённых проверок), `profile_url` (URL публичного профиля или null). `kind` различает email/phone/username/avatar/breach; статусы found/not_found/possible/unknown/unavailable/skipped/disabled. Совместимые прежние разделы результата сохранены; `username_profiles` содержит публичные ссылки подключённых площадок. PDF содержит отдельный раздел username. Поисковые идентификаторы не сохраняются в метаданных заданий или логах. При включённом кабинете email учётной записи сохраняется отдельно, а PDF-копии шифруются и хранятся 30 дней; подробности в ACCOUNTS.md.

Найденный username не доказывает принадлежность профиля заявителю. Отрицательный ответ относится только к конкретному источнику; ограничения и ошибки не превращаются в отсутствие данных. Не гарантируются полнота источников и доступность проверок регистрации. Нормализация здесь — единый формат результатов, не установление личности (этап 4) и не AI-классификация (этап 5).

Документация GitHub: https://docs.github.com/en/rest/users/users#get-a-user . Проверки MVP покрывают найденный/не найденный профиль, чужой username, организации, лимиты/ошибки источника, телефонный адаптер, сочетание трёх идентификаторов, единый формат, разные username в повторах и PDF.


## Этап 2: источники и контроль доступности

Список и ограничения: [SOURCES.md](SOURCES.md). Командные `GET /api/sources` и `POST /api/sources/check` защищены STATUS_API_KEY. Второй endpoint проверяет известные публичные профили и синтетические отрицательные примеры, кеширует ответ на 5 минут и возвращает количество действительно проверенных источников. Секреты и пользовательские идентификаторы в ответ не входят. В PDF утечки подписаны своим провайдером; для LeakCheck общие категории не приписываются отдельной утечке.

На Tilda под формой нужна ссылка Powered by LeakCheck на https://leakcheck.io/ и пояснение передачи данных сторонним источникам. Публичный username проверяется на 14 площадках; один username не устанавливает личность. Хеш email не делает адрес анонимным.

## Оформление PDF

Отчёт использует логотип `assets/privetek-logo.png`, тёмно-синюю и бирюзовую палитру, блоки результатов и нумерацию страниц. Ссылки на профили и источники кликабельны. Изображение логотипа хранится в репозитории и не требует внешнего запроса; при его отсутствии выводится текстовое название PriveTek. Длинные блоки переносятся с учётом фактической высоты текста.

## Этап 4: связи и принадлежность

Новые проверки содержат карточку связей email/телефона/username и находок.
В ЛК пользователь отмечает «Моё / Не моё / Не уверен» и скачивает актуальный PDF.
Отметки не выдаются за независимое установление личности. Алгоритм, API, хранение
и границы: [IDENTITY_RESOLUTION.md](IDENTITY_RESOLUTION.md).

## Этап 5: аналитическая сводка

В новых PDF доступны классификация и объяснимые приоритеты с учётом отметок
принадлежности. Подготовлена отключённая интеграция OpenAI для выбора фактов
сводки. Модель/бюджет и живой пилот ещё не согласованы: этап в работе.
Документация: [AI_LAYER.md](AI_LAYER.md).

## Этап 6: мониторинг

Добровольный еженедельный мониторинг email и одного username, исходные снимки,
история изменений за 90 дней и уведомления только о новых находках. До 10
участников предусмотрено для 28-дневного пилота. Код подготовлен, запуск пилота
требует настройки отдельного расписания. Условия и ограничения описаны в
[MONITORING.md](MONITORING.md).
