# Источники PriveTek — этап 2

Дата проверки: 10 октября 2026 года. В реестре **17 различных сервисов**, из них новая проверяемая основа — **11 публичных username API и LeakCheck Public**. HIBP требует отдельно подключённый ключ; косвенные проверки регистрации зависят от доступности сайтов и не включены в число подтверждённых новых API.

Найденный одинаковый username на разных сайтах **не доказывает**, что профили принадлежат одному человеку. API возвращает минимум, необходимый для проверки: статус, источник, время, публичную ссылку и пояснение. Описания, фотографии, email из публичного профиля, полные ответы API и содержимое утечек не сохраняются в результатах, БД или логах.

Общий ввод username: 1–64 латинских букв/цифр/точек/дефисов/подчёркиваний, начинается с буквы или цифры; начальный `@` удаляется. Регистр сохраняется. Каждый адаптер проверяет свой формат; несовместимый username даёт skipped только для этого сайта. URL и произвольные адреса запросов не принимаются.

## Проверка на сервере

Доступ только команде с тем же Bearer STATUS_API_KEY, что у API заявок:

- `GET /api/sources`: список сервисов, возможностей и признака подключения HIBP; секреты не возвращаются.
- `POST /api/sources/check`: положительные и отрицательные контрольные запросы официальными адаптерами; не принимает пользовательские URL/идентификаторы. Ответ включает время, результаты по источникам и verified_sources. Кеш 5 минут предотвращает повторные массовые запросы. HTTP Cache-Control: no-store.

Положительные публичные примеры: GitHub/octocat, GitLab/sytses, Codeberg/earl-warren, Hugging Face/julien-c, DEV/ben, Hacker News/pg, Keybase/chris, Lichess/thibault, Chess.com/hikaru, Wikipedia/Jimbo_Wales, Discourse Meta/codinghorror. Отрицательный синтетический username: pvtkz8q4n2x7r9. LeakCheck проверяется хешем документированного примера example@example.com; отрицательный пример — хеш stage2-health-pvtkz8q4n2x7r9@example.invalid. Личные данные пользователей для служебной проверки не нужны.

Username-источник засчитывается только при found для известного профиля **и** распознанном JSON-ответе not_found для отрицательного примера. LeakCheck засчитывается при корректном ответе метаданных и not_found для отрицательного примера. Ошибки связи, HTML, неизвестный JSON, чужой username, организации и 429 не засчитываются. Проверка подтверждает работоспособность конкретных запросов на указанную дату, а не полноту результатов для любого пользователя.

Максимум четыре одновременных GET в одном пакете; timeout 12 секунд, без перехода по redirects. LeakCheck ограничен одним запросом/секунду в пределах процесса. Сервис запускается одним worker; несколько реплик потребуют общего ограничителя запросов и очереди (этап 7).

## Критерии приёмки этапа 2

1. В едином результате и PDF есть 10–20 различных проверенных источников.
2. На работающем сервере проверено минимум 10 источников, а ограничения остальных явно отражены.
3. Ошибки не превращаются в «аккаунт отсутствует», совпадения не превращаются в доказательство личности.
4. Тесты покрывают положительные/отрицательные ответы, ложные совпадения, HTML/лимиты, хеш email, отсутствие раскрытия значений утечек и авторизацию служебных проверок.
5. Форма описывает передачу идентификаторов и содержит ссылку на этот документ и Powered by LeakCheck.

Этап 2 — первая подборка источников; добавление новых сервисов и поддержка меняющихся API продолжаются. Закрытые базы, даркнет, собственный индекс, обход CAPTCHA и автоматическое связывание личностей в эту реализацию не входят.
