# Аудит качества источников PriveTek

Аудит проверяет, каким результатам поиска можно доверять и что стоит исправить в первую очередь. Для четырёх источников сравнили ответы адаптеров с тем, что видно в карточке и PDF. Последняя проверка выполнена 27 ноября 2026 года на `d834599f8669cc8dd6d7a9d1409ed0cc1aa81b0d`.

- **GitHub и GitLab по username** - Подтверждают наличие публичного профиля с точным username без учёта регистра. Принадлежность профиля отмечает пользователь.
- **LeakCheck Public по email** - Показывает совпадения по хешу email в каталоге сервиса и возвращает метаданные утечек.
- **Amazon по телефону.** Адаптер распознаёт явное предложение создать аккаунт. Скрытое поле автозаполнения, неоднозначная форма и дополнительная проверка не создают находку.

Для живых проверок использовались публичные профили и контрольные значения. Похожий username, тайм-ауты, HTTP 429 и неожиданные ответы воспроизведены локально на подставных ответах (имитационно). Цель проверки обеспечить гарантию, что сбой отображается как «Проверка недоступна», а распознанное отсутствие совпадений — как «Находок в источнике нет».

## Воспроизведение

**Имитации.** Сценарии отчёта с подставными ответами реализованы в `tests/test_source_quality_audit.py`, сценарии чата — в `tests/test_profile_search.py`. Команда включает локальные тесты стенда.
Для прогона из корня репозитория в окружении с зависимостями `requirements-dev.txt` выполнить:

```sh
python -X utf8 -m pytest -q tests/test_source_quality_audit.py tests/test_profile_search.py tools/source_audit_stand tests/test_source_checks.py tests/test_stage2_sources.py tests/test_report_data.py
```

**Контейнерный стенд для живых тестов.** Один стенд поддерживает два режима. В обоих режимах используется реальное взаимодействие с источниками.

**Ручная проверка от лица пользователя.** Развернуть стенд из корня репозитория.

```sh
docker compose -f tools/source_audit_stand/compose.yaml up --build
```

Откройте локальный кабинет и войдите в один из подготовленных аккаунтов: `example@example.com` или `stage2-health-pvtkz8q4n2x7r9@example.com`. Пароль для обоих — `PriveTek-Audit-2026!`. Журнал показывает этапы заявки, выбранные поля ответов, статусы источников и соответствующие подписи в PDF. [Кабинет](https://127.0.0.1:8443/account/login) · [Инструкция стенда](tools/source_audit_stand/README.md#ручной-запуск)

PDF ручной заявки доступен для скачивания в кабинете. При ручной проверке Amazon стенд по умолчанию сохраняет HTML-снимки ответов в `tools/source_audit_stand/artifacts/amazon-html/<job>/`, где `<job>` — идентификатор заявки из журнала. По снимкам можно сравнить формы до и после отправки номера. Из них удаляются значения полей, параметры URL и скрипты.

**Автоматический тест живых запросов.** Флаг `--verify` запускает три заявки через API кабинета и сверяет статусы GitHub, GitLab и LeakCheck с данными карточки и PDF. В каждом сценарии стенд также проверяет GitHub через API быстрого поиска в чате. Автопрогон передаёт синтетический номер для валидации заявки, а при поиске пропускает Amazon по телефону со статусом `skipped`. Сводка и PDF сохраняются в `tools/source_audit_stand/artifacts/`.

```sh
docker compose -p privetek-source-audit-verify -f tools/source_audit_stand/compose.yaml -f tools/source_audit_stand/compose.verify.yaml up --build --attach app --no-log-prefix --exit-code-from app
```

В консоли каждый сценарий начинается с отдельного заголовка. После прогона выводится блок «Итоги автоматической проверки». Его копия сохраняется в `tools/source_audit_stand/artifacts/verification.txt`.

## Amazon после исправления

- **Явный экран «Создать аккаунт» после отправки номера** даёт `not_found`. В PDF отображается «Находок в источнике нет», карточка находки не создаётся. Это подтверждено тестом на подставном HTML. Скрытый через CSS, неактивный или неоднозначный экран регистрации даёт `unavailable`: неизвестные классы, стили и `inert` не считаются доказательством отсутствия аккаунта. В ручной браузерной попытке такой экран наблюдался, но живой `not_found` через адаптер стенда пока не подтверждён: Amazon направлял его на защитную проверку.
- **Неоднозначная форма входа, скрытое поле пароля или ошибка номера** дают `unavailable` без находки. Редирект на `/ax/aaut/verify/ap/challenge` даёт тот же статус с пояснением «Amazon запросил дополнительную проверку».
- **`possible` пока доступен только для email.** Адаптер распознаёт подтверждённую разметку браузерного шага ввода пароля. Для телефонного сценария такого образца пока нет, поэтому поле пароля не создаёт находку.

Сценарии телефона проверяются в [тестах карточки и PDF](tests/test_source_quality_audit.py), распознавание шага пароля для email — в [тестах адаптеров](tests/test_source_checks.py).

## Приоритеты и наблюдения исходного аудита

1. **Разграничить число записей об утечках и число источников утечек в отчёте LeakCheck.** Выполнено. PDF выводит два счётчика с отдельными подписями, один общий список категорий и название и дату каждого источника.
2. **Доработать подписи категорий LeakCheck.** Известные технические ключи переведены. Неизвестные ключи объединяются под подписью «Другая категория». Сохранение исходных имён неизвестных категорий остаётся открытым вопросом.
3. **Распознавать результат проверки номера в Amazon.** Скрытые поля игнорируются, `Invalid mobile number` распознаётся, неоднозначный ответ даёт `unavailable`. Для оценки положительного сигнала нужен подтверждённый живой пример шага ввода пароля по телефону.
4. **Обработка чужого username.** Если в ответе GitHub/GitLab нет запрашиваемого username, но есть другие, это стоит трактовать как отрицательный сигнал `not_found`. В текущем исполнении, такой сценарий даёт `unavailable`
5. **Различать причины сбоя и отсутствие совпадения.** Для `unavailable` показывать конкретную причину, например тайм-аут, лимит или неподдерживаемый формат. Если для пользовательского отчета достаточно сообщения о недоступности проверки, внутренний журнал требует большей конкретики для дальнейшего анализа и исправления проблем.

**Парсинг веб-страниц**
Amazon использует одну стартовую форму «Sign in or create account» для входа и регистрации. В ручном прогоне от 27 ноября после отправки номера стенд получил HTTP 302 на страницу дополнительной проверки. Скрытое поле пароля было видно на снимке стартовой формы и не создало находку. Прогон с заведомо зарегистрированным номером в живой проверке пока не проводился.

Отдельно для Amazon считаю, что среди целевой аудитории данный источник менее значимый и его приоритет стоит пересмотреть в пользу более распространенных площадок для RU-сегмента

## Охват GitHub

В заявке на отчёт `public_sources.check_profile` обращается к GitHub Users API. Быстрый поиск в чате идёт через `POST /api/account/profile-search` и адаптер публичной HTML-страницы в `profile_search.py`. Оба типа поиска проверяются в каждом живом сценарии, `--verify` сверяет статус и ссылку GitHub в ответе чата. При ручной проверке на стенде также доступны два метода поиска профиля GitHub (отчёт и чат). [Инструкция стенда](tools/source_audit_stand/README.md#ручная-проверка-github-в-чате)

В пяти имитациях — похожий username, CAPTCHA, HTTP 429, тайм-аут и неожиданный HTML — адаптер вернул `unavailable` без ссылки.
