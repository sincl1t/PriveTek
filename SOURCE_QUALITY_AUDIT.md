# Аудит качества источников PriveTek

Аудит проверяет, каким результатам поиска можно доверять и что стоит исправить в первую очередь. Проведен анализ обработки четырех источников - как модуль сканирования отправляет данные, что получает в ответ, как обрабатывает и что показывает в карточке и PDF. Версия приложения `107c2ce`.

- **GitHub и GitLab по username** - Подтверждают наличие публичного профиля с точным username без учёта регистра. Принадлежность профиля отмечает пользователь.
- **LeakCheck Public по email** - Показывает совпадения по хешу email в каталоге сервиса и возвращает метаданные утечек.
- **Amazon по телефону** - Поле пароля на экране входа даёт косвенный признак регистрации.

Для живых проверок использовались публичные профили и контрольные значения. Похожий username, тайм-ауты, HTTP 429 и неожиданные ответы воспроизведены локально на подставных ответах (имитационно). Цель проверки обеспечить гарантию, что сбой отображается как «Проверка недоступна», а распознанное отсутствие совпадений — как «Находок в источнике нет».

## Воспроизведение

**Имитации.** Все имитационные сценарии (вместо реального ответа источника программно подставляются тестовые значения) реализованы в тестовом скрипте (`test_source_quality_audit.py`) 
Для прогона из корня репозитория в окружении с зависимостями `requirements-dev.txt` выполнить:

```sh
python -X utf8 -m pytest -q tests/test_source_quality_audit.py
```

**Контейнерный стенд для живых тестов.** Один стенд поддерживает два режима. В обоих режимах используется реальное взаимодействие с источниками.

**Ручная проверка от лица пользователя.** Развернуть стенд из корня репозитория.

```sh
docker compose -f tools/source_audit_stand/compose.yaml up --build
```

Откройте [кабинет](https://127.0.0.1:8443/account/login) и войдите в один из подготовленных аккаунтов — `example@example.com` или `stage2-health-pvtkz8q4n2x7r9@example.com`. Пароль для обоих — `PriveTek-Audit-2026!`. Весь поток данных при обработке заявки (данные для запроса / данные из ответа / данные в результате обработки / данные отображаемые в отчете) логируется в контейнере. Так после отправки заявки можно посмотреть результат каким его видит пользователь и как он представлен на каждом этапе внутри системы.

PDF ручной заявки доступен для скачивания в кабинете. Автоматический прогон сохраняет скачанные PDF и сводку проверок в `tools/source_audit_stand/artifacts/`. При ручной проверке Amazon стенд по умолчанию сохраняет HTML-снимки ответов в `tools/source_audit_stand/artifacts/amazon-html/<job>/`, где `<job>` — идентификатор заявки из журнала. По снимкам можно сравнить формы до и после отправки номера. Из них удаляются значения полей, параметры URL и скрипты.

**Автоматический тест живых запросов.** Флаг `--verify` запускает встроенный скрипт стенда. Он сам отправляет через API кабинета три заявки с заранее заданными контрольными значениями, проверяет статусы GitHub, GitLab и LeakCheck и сверяет их с текстом PDF. Amazon проверяется вручную. Сводка и PDF сохраняются в `tools/source_audit_stand/artifacts/`.

```sh
docker compose -p privetek-source-audit-verify -f tools/source_audit_stand/compose.yaml -f tools/source_audit_stand/compose.verify.yaml up --build --attach app --no-log-prefix --exit-code-from app
```

В консоли каждый сценарий начинается с отдельного заголовка. После прогона выводится блок «Итоги автоматической проверки». Его копия сохраняется в `tools/source_audit_stand/artifacts/verification.txt`.

**Приоритетные исправления**

1. **Разграничить число записей об утечках и число источников утечек в отчёте LeakCheck.** Выводить два счётчика с отдельными подписями. В контрольном ответе API было 2062 совпавшие записи и 316 источников, а в сводке PDF указано «Записей об утечках: 316». API также возвращает один общий список категорий данных для всех совпавших утечек. Показывать его один раз в сводке, а для каждого источника отдельно выводить название и дату. Сейчас повтор списка под каждым источником создаёт впечатление, что все перечисленные категории относятся к каждой утечке. В отдельном PDF для `example@example.com` список повторился 316 раз, и отчёт занял 52 страницы.
2. **Доработать подписи категорий LeakCheck.** В живом PDF часть категорий остаётся техническими ключами (`city`, `company_name`, `dob` и другие). Понятные подписи с сохранением исходного имени неизвестной категории улучшат читаемость. Общую область действия категорий нужно сохранить: они относятся ко всем совпавшим утечкам, а не к каждой отдельно.
3. **Распознавание реакции Amazon на введенный номер.** Живой тест на не зарегистрированном номере телефона показал, что система даёт ложный положительный сигнал. Просмотр снимков HTML до и после POST номера показал, что сервис использует одну и ту же страницу для Входа/Регистрации, при этом страница содержит скритое поле с именем `password`, на которое реагирует сканер. Признак косвенной регистрации требует пересмотрения. Гипотетические предложения: наложение фильтров на поля для отсеивания скрытых или анализ сообщений об ошибках аутентификации.
4. **Обработка чужого username.** Если в ответе GitHub/GitLab нет запрашиваемого username, но есть другие, это стоит трактовать как отрицательный сигнал `not_found`. В текущем исполнении, такой сценарий даёт `unavailable`
5. **Различать причины сбоя и отсутствие совпадения.** Для `unavailable` показывать конкретную причину, например тайм-аут, лимит или неподдерживаемый формат. Если для пользовательского отчета достаточно сообщения о недоступности проверки, внутренний журнал требует большей конкретики для дальнейшего анализа и исправления проблем.

**Парсинг веб-страниц**
Amazon использует одну стартовую форму «Sign in or create account» для входа и регистрации. На одном и том же контрольном номере стенд в одном прогоне остановился на CAPTCHA, а в других получил Invalid mobile number. При ручной проверке в браузере Amazon предложил создать аккаунт. Скрытое поле пароля уже присутствовало на стартовом экране и поэтому не подтверждает переход к шагу ввода пароля.

Отдельно для Amazon считаю, что среди целевой аудитории данный источник менее значимый и его приоритет стоит пересмотреть в пользу более распространенных площадок для RU-сегмента

**Дублирующие адаптеры источников**

В репозитории остаются две реализации GitHub: рабочая `public_sources.check_profile` и отдельная `source_checks.github_username`. Новые имитации и контейнерный прогон проверяют первую.
