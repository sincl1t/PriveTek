# Аудит качества источников PriveTek

Аудит проверяет, каким результатам поиска можно доверять и что стоит исправить в первую очередь. Для четырёх источников сравнили ответы адаптеров с тем, что видно в карточке и PDF. Проверка выполнена на `884cdad` после слияния с main на `f70b131`

- **GitHub и GitLab по username** - Подтверждают наличие публичного профиля с точным username без учёта регистра. Принадлежность профиля отмечает пользователь.
- **LeakCheck Public по email** - Показывает совпадения по хешу email в каталоге сервиса и возвращает метаданные утечек.
- **Amazon по телефону.** В исходном тесте скрытое поле автозаполнения вызвало ложный сигнал регистрации. Поведение после исправления описано ниже.

Для живых проверок использовались публичные профили и контрольные значения. Похожий username, тайм-ауты, HTTP 429 и неожиданные ответы воспроизведены локально на подставных ответах (имитационно). Цель проверки обеспечить гарантию, что сбой отображается как «Проверка недоступна», а распознанное отсутствие совпадений — как «Находок в источнике нет».

## Воспроизведение

**Имитации.** Все имитационные сценарии (вместо реального ответа источника программно подставляются тестовые значения) реализованы в тестовом скрипте (`test_source_quality_audit.py`) 
Для прогона из корня репозитория в окружении с зависимостями `requirements-dev.txt` выполнить:

```sh
python -X utf8 -m pytest -q tests/test_source_quality_audit.py
```

**Контейнерный стенд для живых тестов.** Один стенд поддерживает два режима. В обоих режимах используется реальное взаимодействие с источниками.

**Ручная проверка от лица пользователя.** Развернуть стенд из корня репозитория.

```sh
docker compose -f tools/source_audit_stand/compose.yaml up --build
```

Откройте локальный кабинет и войдите в один из подготовленных аккаунтов: `example@example.com` или `stage2-health-pvtkz8q4n2x7r9@example.com`. Пароль для обоих — `PriveTek-Audit-2026!`. Для ручной заявки нужен согласованный тестовый номер с кодом страны. Любой номер, прошедший валидацию, запускает проверку Amazon. Журнал показывает этапы заявки, выбранные поля ответов, статусы источников и соответствующие подписи в PDF. [Кабинет](https://127.0.0.1:8443/account/login) · [Инструкция стенда](tools/source_audit_stand/README.md#ручной-запуск)

PDF ручной заявки доступен для скачивания в кабинете. Автоматический прогон сохраняет скачанные PDF и сводку проверок в `tools/source_audit_stand/artifacts/`. При ручной проверке Amazon стенд по умолчанию сохраняет HTML-снимки ответов в `tools/source_audit_stand/artifacts/amazon-html/<job>/`, где `<job>` — идентификатор заявки из журнала. По снимкам можно сравнить формы до и после отправки номера. Из них удаляются значения полей, параметры URL и скрипты.

**Автоматический тест живых запросов.** Флаг `--verify` запускает три заявки через API кабинета и сверяет статусы GitHub, GitLab и LeakCheck с данными карточки и PDF. Автопрогон передаёт синтетический номер для валидации заявки, а при поиске пропускает Amazon по телефону со статусом `skipped`. Сводка и PDF сохраняются в `tools/source_audit_stand/artifacts/`.

```sh
docker compose -p privetek-source-audit-verify -f tools/source_audit_stand/compose.yaml -f tools/source_audit_stand/compose.verify.yaml up --build --attach app --no-log-prefix --exit-code-from app
```

В консоли каждый сценарий начинается с отдельного заголовка. После прогона выводится блок «Итоги автоматической проверки». Его копия сохраняется в `tools/source_audit_stand/artifacts/verification.txt`.

## Amazon после исправления

- **Явный экран «Создать аккаунт» после отправки номера** даёт `not_found`. В PDF отображается «Находок в источнике нет», карточка находки не создаётся. Это подтверждено тестом на подставном HTML. Скрытый через CSS, неактивный или неоднозначный экран регистрации даёт `unavailable`: неизвестные классы, стили и `inert` не считаются доказательством отсутствия аккаунта. В ручной браузерной попытке такой экран наблюдался, но живой `not_found` через адаптер стенда пока не подтверждён: Amazon направлял его на защитную проверку.
- **Неоднозначная форма входа, скрытое поле пароля или ошибка номера** дают `unavailable` без находки. Редирект на `/ax/aaut/verify/ap/challenge` даёт тот же статус с пояснением «Amazon запросил дополнительную проверку».
- **`possible` пока доступен только для email.** Адаптер распознаёт подтверждённую разметку браузерного шага ввода пароля. Для телефонного сценария такого образца пока нет, поэтому поле пароля не создаёт находку.

Сценарии телефона проверяются в [тестах карточки и PDF](tests/test_source_quality_audit.py), распознавание шага пароля для email — в [тестах адаптеров](tests/test_source_checks.py).

## Приоритеты и наблюдения исходного аудита

1. **Разграничить число записей об утечках и число источников утечек в отчёте LeakCheck.** Выводить два счётчика с отдельными подписями. В повторном живом прогоне API вернул 2062 совпадения и 316 источников, а на первой странице PDF появилось «Записи об утечках: 316». PDF занял 57 страниц. API возвращает общий список категорий данных для всех совпавших утечек. Стоит показывать его один раз в сводке и выводить название и дату для каждого источника. Сейчас повтор списка создаёт впечатление, что все перечисленные категории относятся к каждой утечке.
2. **Доработать подписи категорий LeakCheck.** В живом PDF часть категорий остаётся техническими ключами (`city`, `company_name`, `dob` и другие). Понятные подписи с сохранением исходного имени неизвестной категории улучшат читаемость. Общую область действия категорий нужно сохранить: они относятся ко всем совпавшим утечкам, а не к каждой отдельно.
3. **Распознавать результат проверки номера в Amazon.** Игнорировать скрытые поля автозаполнения и отдельно распознавать видимые сообщения об ошибке, например `Invalid mobile number`. Выставлять `possible` при переходе к распознанному шагу ввода пароля. Это уберёт ложный сигнал на общей форме входа и регистрации.
4. **Обработка чужого username.** Если в ответе GitHub/GitLab нет запрашиваемого username, но есть другие, это стоит трактовать как отрицательный сигнал `not_found`. В текущем исполнении, такой сценарий даёт `unavailable`
5. **Различать причины сбоя и отсутствие совпадения.** Для `unavailable` показывать конкретную причину, например тайм-аут, лимит или неподдерживаемый формат. Если для пользовательского отчета достаточно сообщения о недоступности проверки, внутренний журнал требует большей конкретики для дальнейшего анализа и исправления проблем.

**Парсинг веб-страниц**
Amazon использует одну стартовую форму «Sign in or create account» для входа и регистрации. На одном и том же контрольном номере стенд в одном прогоне остановился на CAPTCHA, а в других получил `Invalid mobile number`. При ручной проверке в браузере Amazon предложил создать аккаунт. Скрытое поле пароля уже присутствовало на стартовом экране. Прогон с заведомо зарегистрированным номером в живой проверке пока не проводился.

Отдельно для Amazon считаю, что среди целевой аудитории данный источник менее значимый и его приоритет стоит пересмотреть в пользу более распространенных площадок для RU-сегмента

**Охват GitHub**

Имитации и контейнерный прогон проверяют отчётный адаптер `public_sources.check_profile`, который обращается к GitHub Users API. В репозитории также есть отдельная функция `source_checks.github_username`. Рабочий чат использует адаптер публичной HTML-страницы в `profile_search.py`. Проверка чат-адаптера остаётся отдельной задачей.
