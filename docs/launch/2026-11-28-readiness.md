# Подготовка запуска: Render, SMS.RU, HIBP и мониторинг

Дата проверки: 28.11.2026. Базовый main: `5fa482a6c5213a3c635812d79ef925be19b929bb`.
Это подготовка к запуску, а не разрешение включать платные услуги. Рабочая конфигурация и данные пользователей не изменялись.

Последний deploy live на указанном коммите; автоматическая публикация включена. `/account` отвечает HTTP 200. | Платный тариф не подключён. Раздел настроек требует входа: наличие рабочих ключей и флагов не проверено. Редкие метрики не позволяют оценить рекламную нагрузку. |

Миграция задавала 28 дней один раз, поэтому старое окно могло истечь. Живой цикл мониторинга и доставка уведомления не выполнялись. |

Дополнительно в Render остался бесплатный исследовательский сервис `privetek-maigret-pilot-1116` с отключённой автопубликацией. Он не изменялся.
Логи основного сервиса с уровнем error за доступную часть 28 ноября пустые; это не гарантия отсутствия всех ошибок. Анонимный `/api/internal/monitor/status` вернул 403: подтверждена защита доступа, но не состояние мониторинга.

## Что подготовлено

- SMS: два независимых выключателя, закрытый список телефонов пилота по HMAC, максимум 10 принятых попыток отправки в сутки по умолчанию, пять попыток ввода кода, срок кода пять минут, ограничение повторного запроса и существующие лимиты API.
- Телефон хранится зашифрованно; поиск владельца — по HMAC. Привязка и отвязка требуют сессию, CSRF и пароль. Код одноразовый, аккаунты изолированы. Неизвестный номер не получает SMS и не создаёт аккаунт.
- Неудачная/неопределённая отправка не повторяется автоматически и расходует дневной лимит. Ответ SMS.RU о приёме не равен подтверждению доставки на телефон.
- SMS-поля скрыты, пока не заданы оба флага, ключ и список пилота. Email остаётся способом регистрации и восстановления.
- HIBP: явный выключатель, минимальный интервал, учёт `Retry-After`, безопасные статусы ошибок, отдельный инструмент исключительно для официальных синтетических адресов.
- Мониторинг: `--check` для runner (только GET статуса), план ресурса без его создания, отдельная процедура обновления окна пилота с режимом чтения по умолчанию и запретом изменений при активных подписках.
- Инвентаризация настроек выводит только наличие ключей, а не их значения; по умолчанию не обращается к БД или провайдерам.

## Порядок включения после согласования

1. Согласовать отдельную публикацию этого PR. До слияния сделать актуальную резервную копию БД по принятой процедуре и проверить восстановление; не менять `ACCOUNT_SECRET` и `ACCOUNT_REPORT_KEY`. При публикации автоматически применится добавочная миграция `014_phone_auth.sql` (существующие аккаунты не переписываются).
2. В Render проверить masked-поля настроек, подключения БД/почты и доступность через Timeweb. Согласовать тариф web-сервиса и способ оплаты. Переключение тарифа не заменяет проверку из российских сетей.
3. Оставить `SMS_AUTH_ENABLED=false`, `SMS_LIVE_SEND_ENABLED=false`, `HIBP_ENABLED=false`, `MONITOR_ENABLED=false`. Не загружать `.env.example` поверх рабочих настроек. Выполнить `python tools/launch_readiness.py --database` в доверенной среде сервиса; результат не содержит секретов.
4. SMS.RU: зарегистрировать/подтвердить командный аккаунт, уточнить цену, разрешённого отправителя и условия авторизационных SMS. Сохранить `SMS_RU_API_ID` только в секретах web-сервиса. Согласовать номера пилота и дневной лимит. Для каждого нормализованного E.164 номера получить `phone_auth.phone_key(number)` с **тем же** `ACCOUNT_SECRET`, записать HMAC через запятую в `SMS_PILOT_PHONE_HASHES`. Не помещать номера или ключи в git/логи. `SMS_PROVIDER=sms_ru`, `SMS_MAX_SENDS_PER_DAY=10` либо отдельно согласованный меньший лимит.
5. Только после согласования расходов включить оба SMS-флага для разрешённых номеров. Подтвердить номер в настройках аккаунта; проверить получение кода на телефоне, вход с существующим вторым фактором, неверный/истёкший код, отвязку, вход по email и расход в кабинете SMS.RU. Сначала один тестовый аккаунт. Статус приёма API не выдавать за доставку.
6. HIBP: выбрать подписку под ожидаемое число проверок и согласовать расходы. Ключ хранить в `HIBP_API_KEY`, интервал `HIBP_MIN_INTERVAL_SECONDS` подобрать по оплаченному RPM с запасом. Для 10 RPM пример — 6.5 секунды. Включить `HIBP_ENABLED=true` только при отдельном разрешении и проверить согласованный тестовый email. Наличие ключа при пустом флаге сохраняет прежнее поведение: для гарантированного выключения нужен явный `false`.
7. Ограничение HIBP сейчас действует в одном Python-процессе. Не увеличивать число процессов/реплик до общего ограничителя (отдельный PR очереди №24). При частых запросах проверка честно показывает недоступность; автоматической отложенной обработки в этой доработке нет.
8. Мониторинг: при `MONITOR_ENABLED=false` прочитать `python tools/monitor_pilot_window.py`. Если окно истекло и активных подписок нет, после разрешения выполнить `--days 28 --apply`. Если есть активные подписки — сначала согласовать их судьбу; инструмент ничего не переписывает. Он не подключает пользователей автоматически.
9. Создать cron **только после одобрения бюджета** по `launch/monitor-service-plan.json`: 03:00 UTC, максимум 600 секунд, отдельный `MONITOR_RUNNER_TOKEN` (одинаковый на web и cron). Ключи БД, почты, SMS, HIBP новому cron не передавать. Это план, не файл для автоматического применения.
10. Выполнить `python tools/run_monitor.py --check` с токеном в закрытой среде, затем после разрешения включить мониторинг и одну подписку тестового аккаунта. Проверить базовую проверку → синтетическое изменение → одно уведомление → отсутствие повторной рассылки → паузу. Подтвердить письмо получателем. Только после этого расширять пилот.

## Остановка и ограничения

- SMS: выключить оба SMS-флага, оставить email-вход; новые и уже выданные SMS-коды не принимаются. Существующие сессии сохраняются.
- HIBP: `HIBP_ENABLED=false`; результат — «не проверялось», а не отрицательный.
- Мониторинг: `MONITOR_ENABLED=false`, затем приостановить cron, проверить отсутствие новых задач. Отмена флага не гарантирует прерывания уже выполняющегося внешнего запроса.
- Нельзя обещать «останется только оплатить»: ещё нужны ключи, подтверждения у провайдеров, проверка рабочих настроек и короткие живые проверки после отдельного разрешения.
- Тесты SMS имитационные, HIBP — реальные только на официальных синтетических адресах. Нагрузочная проверка платных источников, массовые SMS и production-поиски не проводились.
